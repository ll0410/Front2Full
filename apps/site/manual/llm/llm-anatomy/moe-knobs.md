# MoE 的三个旋钮 · 专家数、激活数、共享专家

> 同样是 MoE，DeepSeek 的“多而小 + 共享专家”、Llama 4 的“少而大”、Qwen3 的“砍掉共享专家”（以及 Qwen3.8 重新加回）为什么差这么多？拆开三个可调旋钮——专家总数与粒度、每 token 激活几个、要不要一个万金油共享专家——看各家的取舍逻辑。

“把前馈换成一堆专家”只是一句口号。真正把各家 MoE 区分开的，是三个可调的旋钮。把它们拧到不同位置，就得到 DeepSeek、Llama 4、Qwen、Kimi 那几种截然不同的风格。这一章，一个旋钮一个旋钮地拧。

## 旋钮一：专家“多而小”还是“少而大”

同样是 MoE 层，你可以拆成**很多个小专家**，也可以拆成**几个大专家**。两种极端并存：

| 模型 | 路由专家总数 | 单个专家的中间维度 | 风格 |
| --- | --- | --- | --- |
| **DeepSeek-V3**（2024） | **256** | 2048（小） | 多而小（细粒度） |
| **Qwen3 235B**（2025） | 128 | 中等 | 偏多 |
| **Llama 4 Maverick**（2025） | **8** | 8192（大） | 少而大 |
| **DeepSeek V4.1-Flash**（2026） | **384** | 2048（小） | 超细粒度 |
| **Qwen3.8-Max**（2026） | **512** | 2048（小） | 超细粒度 |
| **Kimi K3 / K3.1 Pro**（2026） | **896** | 3072（在 3584 维潜空间内计算） | 极细粒度 + 潜空间压缩 |

DeepSeek 走的是**细粒度（fine-grained）**路线：把前馈切成几百个小专家；到了 2026 年，Qwen3.8-Max（512 个专家）和 Kimi K3（896 个专家）更是把细粒度推到了极致。Llama 4 则走的是**经典**路线：8 个大专家。

为什么前沿旗舰越来越偏爱“多而小”？**DeepSeekMoE 论文**的论证很妙：专家越多、越小，**能组合出的“专家搭配”就越多**。8 选 2，只有 28 种组合；256 选 8、乃至 896 选 16，组合数是个天文数字。组合空间越大，不同 token 越能被路由到**更贴合自己**的专家子集，专家也越能各自**深度专精**（一个管代码缩进、一个管化学式、一个管古文……），而不是每个都被迫当“样样通样样松”的万金油。

代价是：小专家越多，跨卡通信（All-to-All）压力越大。[Kimi K3 的 LatentMoE](https://daiw.org/manual/kimi-k3/latent-moe) 为此专门加了一招：先把 7,168 维的 token 投影压到 3,584 维的**潜空间**，再分发给 896 个路由专家计算，直接把跨卡通信体积砍半。

## 旋钮二：每个 token 激活几个（top-k）

选出总专家后，还要定**每个 token 实际激活几个**。这个数直接决定“每步算多少”：

| 模型 | 每 token 激活（路由专家） | 备注 |
| --- | --- | --- |
| Switch Transformer | **1** | 最省，top-1 |
| Llama 4 Maverick | **2** | |
| DeepSeek-V3 | **8** | + 1 个共享（见旋钮三）= 实际 9 个 |
| Qwen3 235B | **8** | 无共享专家 |
| DeepSeek V4.1-Flash | **6** | + 1 个共享 = 实际 7 个（384 选 6） |
| Qwen3.8-Max | **10** | + 1 个共享 = 实际 11 个（512 选 10） |
| Kimi K3 / K3.1 Pro | **16** | + 2 个全维度共享专家（896 选 16） |

激活越多，每个 token 能调用的“脑力”越多、表达越强，但每步计算也越大。这就是**上一章那张“总参数 vs 激活参数”表背后的旋钮**。

::: info

旋钮一和旋钮二要**一起看**。DeepSeek 的“256 个小专家、激活 8+1”和 Llama 4 的“8 个大专家、激活 2”，可能激活参数量相近，但**风格迥异**：前者是“从一大群专才里点几个”，后者是“从几个通才里点一两个”。前者赌的是“专精 + 组合”，后者赌的是“简单 + 稳健”。

:::

## 旋钮三：要不要一个“万金油”共享专家

这是最能体现设计哲学分歧与演进的一个旋钮。

**共享专家（shared expert）**是一个**永远激活、每个 token 都过**的专家，叠在路由选出的那几个之上。DeepSeek、GLM-4.5、Kimi K2/K3 都留了共享专家（1 到 2 个）。

它的道理是：**语言里有大量“谁都用得到”的通用知识**（基本语法、常见搭配）。如果没有共享专家，那这些通用能力就得**在每个路由专家里各学一遍**——冗余、浪费。给一个专家“专门负责通用”，常驻在线，就把通用知识从路由专家身上卸下来，**让路由专家腾出手去专精**。分工更干净。

有趣的是 **Qwen 家族在这一旋钮上的往返**：
- **Qwen2.5-MoE** 用了共享专家；
- **Qwen3（2025）偏偏把共享专家砍了**——团队在报告里坦诚说，当时在 128 专家的规模下没观察到足够明显的收益，于是干脆去掉图个简单；
- **到了 2026 年的 [Qwen3.8-Max](https://daiw.org/manual/qwen3-8-max/architecture)（512 个路由专家，稀疏度降到约 2%），共享专家又被重新请了回来**（`512 routed + 1 shared`）！因为当路由专家拆得极细、每个路由专家被激活的概率极低时，常驻的共享专家成了兜住高频公共变换的压舱石。

**这一去一回，恰恰是读架构最有意思的信号**：同一个设计不是绝对的“对”或“错”，而是在不同的专家粒度与稀疏度下，它的边际收益完全不同。

## 三个旋钮，拧出不同性格

把三个旋钮并到一张表，各家的“性格”就跃然纸上：

| 模型 | 专家（总/激活） | 粒度 | 共享专家 | 一句话性格 |
| --- | --- | --- | --- | --- |
| **DeepSeek-V3 / V4.1-Flash** | 256/8 → 384/6 | 小（细粒度） | 有（1） | 多而小 + 共享：极致专精与组合 |
| **Llama 4 Maverick** | 8 / 2 | 大 | 无 | 少而大：经典、稳健、好实现 |
| **Qwen3 235B** | 128 / 8 | 中 | **无（主动砍掉）** | 偏多但从简 |
| **Qwen3.8-Max** | 512 / 10 | 小（超细粒度） | **有（1，重新加回）** | 超细粒度下请回共享专家兜底 |
| **Kimi K3 / K3.1 Pro** | 896 / 16 | 小（潜空间） | 有（2 个全维） | LatentMoE 潜空间路由省通信 |
| **GLM-4.5** | 多 | —— | 有 | 借鉴 DeepSeek 路线 |

读到这儿，你应该有个体会：**“用不用 MoE”只是第一层；真正见功力的是这三个旋钮怎么拧。** 而拧法背后，是各家对“专精 vs 简单”“组合能力 vs 跨卡通信成本”的不同下注。

## 还差一块：拧完旋钮，怎么让它训得起来

三个旋钮定了 MoE 的“形状”，但 MoE 有个众所周知的老大难：**训练时，路由器很容易“偏心”**——把绝大多数 token 都塞给少数几个热门专家，剩下的专家“饿死”、学不到东西，几百个专家白设。这叫**负载不均衡**，是 MoE 能不能训好的命门。各家（尤其 DeepSeek）为此发明了一整套招数，包括一个漂亮的“无辅助损失”方案。这是下一章。👉 [让 MoE 训得稳、又均衡](/manual/llm/llm-anatomy/moe-stability)
